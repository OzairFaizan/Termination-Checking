\chapter{Design and Approach}
%%%%%%%%%%%%%%%%%%%%%%%%

The checker is implemented entirely within the Scala 3 compiler as a
\texttt{MiniPhase}, operating directly on the typed abstract syntax tree (AST)
produced by earlier compiler phases. It does not rely on any external solver,
rewriting engine, or verification framework. All information needed is obtained
through the compiler's own symbol and type APIs. This makes the checker
lightweight, and immediately available to any project that uses the Scala 3
compiler, without additional installation or configuration.

Furthermore, unlike proof assistants that enforce termination globally, this
checker is entirely opt-in. This aligns with the needs of a general-purpose
language like Scala, where the overhead of proving the termination of every
method is impractical.
The phase is enabled by the \texttt{-Ycheck-termination} compiler flag and only
methods annotated with \texttt{@terminates} and methods called by the annotated
methods are checked.
Additionally, the phase requires the bodies of functions for the analysis in
order to inline function calls, as such, the \texttt{-Yretain-trees} flag is
required to retain the ASTs of the definitions' bodies, since otherwise only
signatures of definitions are kept.

Termination contract can be enabled at the interface level. The checker enforces
that all overriding methods inherit the \texttt{@terminates} annotation. If an
overriding method omits it, an error is thrown, ensuring that termination
intents stated at the interface level are maintained.

\section{Conservative, Sound Analysis}
The checker prioritizes soundness over completeness: it will never accept
non-terminating methods, however, it may reject methods that do in fact
terminate.
During the AST traversal, the checker assigns every value a \texttt{Size}
(either \texttt{Smaller}, \texttt{Same}, or \texttt{Unknown}) relative to the
parameters of the method, then, at each recursive call, the arguments to the
call are compared lexicographically to the method's parameters. However, the
sizes are inferred syntactically, meaning that we only track a decreasing size
when selecting fields of ADTs. Because other measures such as those that 
require reasoning about arithmetic are out of scope, the checker will reject
programs that terminate if the termination relies on such semantic properties.

\section{Escape Hatches}
Because the analysis is conservative, rather than forcing developers to
restructure their code for the benefit of the checker, escape hatches are
provided as annotations, shifting the analysis on the developer. Misuse of these
escape hatches can cause the checker to accept a non-terminating function, so
they should be used with care.

The \texttt{@assumeTerminates} annotation applied to a method causes the checker
to accept any call to that method without inspecting its body. This is
especially useful for Scala's standard library methods whose bodies are
unavailable. For instance, primitive operators like addition terminate
but their body is not available for analysis:
\begin{minted}{scala}
        @assumeTerminates
        def +(x: Int): Int
\end{minted}

The \texttt{uncheckedTermination} method allows the user to wrap a block that is
not checked, this is useful for wrapping calls to external libraries when the
source is unavailable to the user. Here we bypass the termination check for an
external function call while keeping the rest of the recursive method verified:
\begin{minted}{scala}
        @terminates
        def sum_f(l: List[Int]): Int =
          l match
            case Nil => 0
            case hd :: tl => uncheckedTermination(external_f(hd))) + sum_f(tl)
\end{minted}

The \texttt{@assumeDecreases} annotation applied to a method (typically a field
accessor or a selector-like method), tells the checker that the called method on
a value outputs a result that is strictly smaller than that value.
This is useful when it's semantically clear that the value decreases, but the
simple structural analysis fails. In this example, the annotation asserts
that \texttt{getLeftOrElseRight} yields a structurally smaller value:
\newpage
\begin{minted}{scala}
        sealed trait Tree:
          @assumeDecreases
          def getLeftOrElseRigth: Tree = this match
              case Node(left: Node, _) => left
              case Node(Leaf, right) => right
              case _ => Leaf
              
        case class Node(left: Tree, right: Tree) extends Tree
        case object Leaf extends Tree
\end{minted}

The \texttt{@assumeWellFounded} annotation applied to a type bypasses the
well-foundedness check, asserting that the type admits no infinite descending
chains. It is needed for types that are structurally well-founded but whose
shape does not match the simple syntactic criterion the checker applies.
This allows us to mark the standard library \texttt{List} as well-founded
regardless of the implementation details:
\begin{minted}{scala}
        @assumeWellFounded
        sealed abstract class List[+A]
\end{minted}

%%%%%%%%%%%%%%%%%%%%%%%%
\chapter{Implementation}
%%%%%%%%%%%%%%%%%%%%%%%%

The checker is implemented as a \texttt{MiniPhase} inside the
\texttt{dotty.tools.dotc.transform} package.
A \texttt{MiniPhase} is a compiler phase designed so that several mini phases
can be merged into a single AST traversal for efficiency \cite{MiniPhase}.
When a method is annotated with \texttt{@terminates}, is not abstract
(\texttt{Deferred}), and has not already been verified in a prior traversal, the
methods body is traversed. Successfully checked methods are accumulated in a
\texttt{checked} set shared across all invocations of the phase. A method that
has already been certified is not re-examined when it is called by another
annotated method. The phase is entirely inactive unless the
\texttt{-Ycheck-termination} compiler flag is set, ensuring zero overhead for
projects that do not opt in.

\section{Structural Decrease Analysis}
The core analysis tracks how the sizes of values evolve as execution proceeds.
A \texttt{valMap} associates local value symbols to a \emph{(source, size)}
pair, recording where the value came from and whether it is \texttt{Smaller}
or \texttt{Same} relative to that source. An analogous \texttt{varMap} tracks
mutable variables, updated at every assignment.

\subsection{Pattern Matching and ADTs}
Pattern matching on an Algebraic Data Type is the primary mechanism by which
structural decrease is established. When the selector of a \texttt{match} has
a synthetic \texttt{unapply} method, i.e., one generated automatically by the
compiler for a \texttt{case class} or \texttt{enum}, the checker knows that
the binders introduced by each pattern are strict sub-value of the
selector. The method \texttt{mapMatchedSymbols} walks the pattern tree. The
outermost binder (the variable that names the whole matched value) is recorded
as \texttt{Same} size as the selector, while any nested binders (the fields
extracted from the constructor) are recorded as \texttt{Smaller}.
If the \texttt{unapply} method is user-defined (not synthetic), the checker
cannot guarantee that deconstruction actually yields a smaller value, and
emits a warning, and does not consider the sub-value as \texttt{Smaller}.

\subsection{Field Access and \texttt{peelSelects}}
Beyond pattern matching, a decrease can also be established by selecting a
field of a value. The helper \texttt{peelSelects} resolves a chain of
field-access expressions back to an original symbol and determines whether a
decrease occurred along the way. A field selection is considered to decrease
the size of the value when the selected field's name corresponds to a
constructor parameter of a \texttt{case class}, or when the field's method is
annotated with \texttt{@assumeDecreases}.

\subsection{Verifying Polymorphic Method Calls}
Object-oriented languages like Scala heavily utilize subtype polymorphism, where
a method called on a value of a static type (such as a sealed trait or abstract
class) is dynamically dispatched at runtime to a concrete implementation. This
introduces a verification challenge not typically present in proof assistants
like Rocq or Lean. Because our checker operates at compile time, it cannot
definitively know which concrete method will be invoked at runtime.

In the presence of dynamic dispatch, the checker must over-approximate the
possible runtime behaviors. When a method call is encountered on a polymorphic
type, the checker leverages Scala's \texttt{sealed} keyword, which restricts the
set of possible subtypes to a known, finite set. The
\texttt{methodOverrides} routine enumerates all sealed strict descendants of the
static type and resolves the method name within each descendant's type. If any
overrides are found, the checker verifies each one independently. A polymorphic
call is accepted only if \emph{every} possible concrete implementation it could
dispatch to is proven to terminate. By exhaustively checking the sealed
hierarchy, the checker guarantees that whichever method is dynamically
dispatched at runtime is safe. If even a single overriding method fails the
termination check or if the hierarchy is not sealed, meaning an unknown subclass
could be loaded at runtime the checker conservatively rejects the call.

\subsection{Well-Foundedness}
A structural decrease is only a valid termination argument if the type being
decreased is well-founded, that is, it admits no infinite descending chain of
sub-values. The checker enforces this via \texttt{typeWellFounded}. A sealed
type is well-founded when all of its children are well-founded. A case object
(a leaf of an ADT) is trivially well-founded. A case class is well-founded
when all of its fields are stable members that correspond directly to
constructor parameters. If the type is not well-founded, the checker emits a
warning and considers the value of size \texttt{Unknown}.

\subsection{Lexicographic Ordering}
When checking a recursive call, the method \texttt{areSmaller} compares the list
of arguments against the list of parameters of the recursive method in order. It
calls \texttt{isLexicoDecreasing}, which steps through the argument–parameter
pairs. If the first pair is \texttt{Smaller}, the check succeeds provided the
type is well-founded. If it is \texttt{Same}, the check proceeds to the next
pair. If it is \texttt{Unknown}, the check fails. The ordering of the pairs can
be controlled by the \texttt{@decreases} annotation, which specifies an ordering
of parameters to use as the measure, overriding the default left-to-right order.


\section{Mutual Recursion}
The checker handles mutual recursion by inlineing called methods. A
\texttt{callStack} tracks the methods currently being analyzed. When a call to a
method is encountered, the checker first looks it up in \texttt{callStack}.
If it is already present, the call is recursive (possibly mutual) and
\texttt{areSmaller} is invoked to verify the decrease. If the method is not yet
on the stack, \texttt{traverseCalled} is invoked, which pushes the callee onto
the stack, maps the actual arguments to the callee's parameters in
\texttt{valMap}, traverses the callee's body, and then restores the stack and
map. This allows the checker to follow chains of mutual recursion of arbitrary
depth.


\section{While Loops}
While loops are treated separately from recursive calls. Since they rely on
mutable variable. The checker performs two traversals. In the first traversal,
call checking is disabled and \texttt{varMap} is reset to empty. The purpose of
this traversal is to determine whether there exists a variable that is assigned
a strictly smaller value (with respect to itself) inside the loop body. If such
a variable exists the loop terminates. Note that since well-founded types cannot
decrease indefinitely, we have two possible cases. Either the loop condition
becomes false, hence, the loop terminates. Or we hit a leaf of the ADT and the
assignment to a strictly smaller value results in an exception being thrown
(this is the case for e.g. \texttt{Nil.tail}) or the \texttt{@assumeDecreases}
escape hatch was wrongly used.
The checker then proceeds to a second traversal with call checking re-enabled,
and the original \texttt{varMap} restored so that any recursive calls inside the
loop body are themselves verified to be terminating.

\subsection{\texttt{varMap} Updates}
An \texttt{Assign} node records \texttt{Smaller} in \texttt{varMap} if
\texttt{areSmaller} can confirm the right-hand side is smaller than the current
value of the variable, and \texttt{Unknown} otherwise.

For branching and looping constructs, the checker explores each branch
independently and then merges the results where the worst-case size is kept.
Concretely, when traversing an \texttt{If} expression or \texttt{Match} cases,
we compute one \texttt{varMap} for each branch, then, for each variable in the
union of all maps, it is considered \texttt{Unknown} if \texttt{Unknown} in
any branch, \texttt{Smaller} if \texttt{Smaller} in all branches and
\texttt{Same} otherwise. Then the original \texttt{varMap} is updated with the
new information from the branching construct.
For \texttt{WhileDo}, the body may never be executed, therefore, we merge
the original \texttt{varMap} with a \texttt{varMap} computed by traversing the
body of the loop.

\section{Performance Evaluation}
To evaluate the compile-time overhead introduced by the checker, benchmarks were
run on a file containing approximately 30 functions. These benchmarks were
conducted on a personal computer while no other processes were running to ensure
the accuracy and consistency of the measurements.
The compilation was measured across three scenarios: using no flags to
completely disactivate the phase, using only the \texttt{-Yretain-trees} flag to
measure the overhead of keeping the AST in memory, and using both
\texttt{-Yretain-trees} and \texttt{-Ycheck-termination} to fully activate the
checker.

The benchmarks show that the checker has little overhead. Retaining the trees

is negligible. This confirms that the goal of being lightweight is achieved.


\section{What the Checker Can Verify}

\subsection{Simple Structural Recursion}
The most direct case is a recursive function that pattern-matches on an ADT and
recurses on a field extracted by that match.
\begin{minted}[escapeinside=||]{scala}
        sealed abstract class Nat
        case object Zero extends Nat
        case class Succ(val n: Nat) extends Nat

        @terminates
        def f(n: Nat): Boolean =
          n match
            case Zero => false
            case Succ(pn) => f(pn)
\end{minted}
When the checker encounters the \texttt{match} on \texttt{n}, it identifies a
synthetic \texttt{unapply} method, and records \texttt{pn} as \texttt{Smaller}
than \texttt{n} in \texttt{valMap}.
At the recursive call \texttt{f(pn)}, \texttt{areSmaller} determines that the
argument \texttt{pn} is \texttt{Smaller} than the parameter \texttt{n}, and
\texttt{typeWellFounded} confirms that \texttt{Nat} is a well-founded type.
The recursive call is therefore accepted.

\subsection{Lexicographic Decrease and \texttt{@decreases}}
Some functions require lexicographic ordering. For the Ackermann function
the parameter \texttt{n} decreases in some calls, while in others \texttt{n}
stays the same but \texttt{m} decreases.
\begin{minted}[escapeinside=||]{scala}
        @terminates
        def ackermann(n: Nat, m: Nat): Nat =
          n match
            case Zero => Succ(m)
            case Succ(pn) =>
              m match
                case Zero => ackermann|\circled{1}|(pn, Succ(Zero))
                case Succ(pm) => ackermann|\circled{2}|(pn, ackermann|\circled{3}|(n, pm))
\end{minted}
For \circled{1} and \circled{2}, the checker sees \texttt{pn} is
\texttt{Smaller} than \texttt{n} and immediately accepts. For \circled{3},
\texttt{n} is \texttt{Same}, so \texttt{isLexicoDecreasing} advances to the
second position and finds \texttt{pm} is \texttt{Smaller} than \texttt{m}. All
three recursive calls are therefore accepted.
One limitation we see here, is that we must match on one value at a time and
matching over tuples is not supported.

When the decreasing argument is not the first, \texttt{@decreases} can be used
to tell the checker to use a different ordering:
\begin{minted}[escapeinside=||]{scala}
        @terminates
        def f(logger: List[Nat], n: Nat): (Nat, List[Nat]) @decreases(n) =
          n match
            case Zero => (Zero, Zero :: logger)
            case Succ(pn) => f(n :: logger, pn)
\end{minted}
Without \texttt{@decreases(n)}, the checker would compare \texttt{n :: logger}
to \texttt{logger} first, find the size unknown, and reject the call. With the
annotation, it checks \texttt{n} first, finds \texttt{pn} is \texttt{Smaller},
and the call is accepted.
Note that the annotation is on the output type to allow the use of function
parameter symbols in the annotation parameters.

\subsection{Mutual Recursion} \label{sec:mutualRec}
\begin{minipage}[t]{0.45\textwidth}
    \begin{minted}[escapeinside=||]{scala}
    @terminates
    def isEven(n: Nat): Boolean =
      n match
        case Zero => true
        case Succ(pn) => isOdd(pn)
    \end{minted}
\end{minipage}\hfill
\begin{minipage}[t]{0.45\textwidth}
    \begin{minted}[escapeinside=||]{scala}
    @terminates
    def isOdd(m: Nat): Boolean =
      m match
        case Zero => false
        case Succ(pm) => isEven(pm)
    \end{minted}
\end{minipage}

When \texttt{isEven} calls \texttt{isOdd}, the checker pushes \texttt{isOdd}
onto \texttt{callStack} and maps argument \texttt{pn} to parameter \texttt{m} of
\texttt{isOdd}. Inside \texttt{isOdd}'s body it finds the call
\texttt{isEven(pm)}. At this point \texttt{isEven} is already on
\texttt{callStack}, so the call is flagged as (mutually) recursive and
\texttt{areSmaller} is called. The argument passed to \texttt{isEven} is the
\texttt{pm}, and we have the following chain of size inequalities asserting
\texttt{pm} is \texttt{Smaller} than \texttt{n}: $\texttt{pm} < \texttt{m} =
\texttt{pn} < \texttt{n}$. Therefore, both functions are shown to be
terminating.

\subsection{Higher-Order Functions} \label{sec:HOF}
The checker can follow higher-order calls when the closure is available.
\newpage
\begin{minted}[escapeinside=||]{scala}
  sealed trait MyList[+A]:
    def foldRight[B](z: B)(op: (A, B) => B): B = this match
        case MyNil => z
        case MyCons(hd, tl) => op(hd, tl.foldRight(z)(op))
  case object MyNil extends MyList[Nothing]
  case class MyCons[+A](val hd: A, val tl: MyList[A]) extends MyList[A]

  sealed trait Expr
  case class Const(c: Int) extends Expr
  case class Add(args: MyList[Expr]) extends Expr

  @terminates
  def addAll(e: Expr): Int =
    e match
      case Const(c) => c
      case Add(args) => args.foldRight(0)((l, acc) => addAll(l) + acc)
\end{minted}
When \texttt{foldRight} is inlined and the checker encounters the application of
\texttt{op}, \texttt{getMethodSymbol} resolves it back to the anonymous
function \texttt{(l, acc) => addAll(l) + acc}. Inside that definition, the
recursive call \texttt{addAll(l)} uses \texttt{l}, which is \texttt{Smaller}
than \texttt{e} by the following chain of size inequalities:
$\texttt{l} = \texttt{hd} < \texttt{this} = \texttt{args} < \texttt{e}$.
Furthermore, \texttt{foldRight} terminates as its \texttt{this} arguments
decreases. We can view this as mutual recursion: \texttt{addAll} calls
\texttt{foldRight} and \texttt{foldRight} calls \texttt{addAll} through
\texttt{op}. Note, Stainless is currently unable to prove termination in this
case and provides a counter-example which is false.

\subsection{While Loops}
A while loop terminates if some mutable variable is unconditionally assigned a
strictly smaller value in every iteration.
\begin{minted}[escapeinside=||]{scala}
        @terminates
        def f(a: List[Int]): Int =
          var res = 0
          var l = a
          while (!l.isEmpty) {
            l = l.tail
            res += f(l)
          }
          res
\end{minted}
In the first traversal, the checker processes the assignment
\texttt{l = l.tail}, \texttt{peelSelects} resolves all possible \texttt{tail}
methods/values and checks whether they are constructor parameters or annotated
with \texttt{@assumeDecreases}. In this case we have annotated the standard
library \texttt{tail} methods of \texttt{List}. Since a decreasing variable
exists, the loop is accepted. The second traversal then verifies that the
recursive calls inside the loop body also terminate.

\section{What the Checker Cannot Verify}
\subsection{Semantic Termination Arguments}
Because sizes are inferred syntactically, the checker rejects any function whose
termination depends on semantic properties.
\begin{minted}[escapeinside=||]{scala}
        @terminates
        def f(a: List[Int]): Int =
          a match
            case Nil => 0
            case _ => g(a)
        def g(a: List[Int]): Int =
          a match
            case Nil => f(a) // error
            case hd :: tl => hd + f(tl)
\end{minted}
Here, \texttt{f} terminates, however, the recursive call \texttt{f(a)} in
\texttt{g} is rejected by the checker since its unaware that the call
\texttt{g(a)} cannot be reached as \texttt{a = Nil}.

\begin{minted}[escapeinside=||]{scala}
        @terminates
        def h(a: List[Int]): Int =
          var res = 0
          var l = a
          while (!l.isEmpty) { // error
            res += l.head
            if true then l = l.tail
          }
          res
\end{minted}
Similarly, here \texttt{l} is only assigned \texttt{l.tail} in one branch of the
\texttt{if}. After merging the two branches, \texttt{varMap} records \texttt{l}
as \texttt{Same} (since the else branch does not decrease it), and the checker
rejects the loop, even though the condition \texttt{true} means the else branch
is dead code. The checker is purely syntactic and does not evaluate conditions.

\subsection{Cross-Parameter Size Tracking}
The checker does not support swapping decreasing arguments.
\begin{minted}[escapeinside=||]{scala}
        @terminates
        def i(n: Nat, m: Nat): Nat =
          n match
            case Zero => Zero
            case Succ(pn) =>
              m match
                case Zero => Zero
                case Succ(pm) => i(pm, pn) // error
\end{minted}
The function \texttt{i} terminates, it can be seen by unrolling the recursive
call. However, when the recursive call \texttt{i(pm, pn)} is found, the method
\texttt{areSmaller} compares \texttt{pm} with \texttt{n} which results in
\texttt{Unknown}. 
This highlights a fundamental limitation of the checker's structural analysis,
as it verifies sizes strictly on a per-parameter basis. Techniques such as
size-change termination, or the SMT-driven bounds analysis used by Stainless,
can handle these cross-parameter cases but come with a higher computational
overhead.

\chapter{Correctness}
%%%%%%%%%%%%%%%%%%%%

In this chapter we give a correctness sketch for the termination checker. We use
the term \emph{termination} to mean that a function either returns a value or
throws an exception. Infinite loop or recursion are the only failure modes the
checker is concerned with.
Under this definition, a thrown exception counts as a form of termination,
because the function does eventually stop executing.
Correctness in this context means \emph{soundness} under any assumptions made by
escape hatches, i.e., if the checker accepts a method, then that method
terminates in the sense defined above, conditional on all assertions made.

\section{Simple Recursion}
Consider a method \texttt{f} with parameters $p_1, \ldots, p_k$ that has been
accepted by the checker. By construction, every call within \texttt{f}'s body
that is detected as recursive must pass \texttt{areSmaller}, which asserts that
the argument tuple $(a_1, \ldots, a_k)$ is lexicographically smaller
than $(p_1, \ldots, p_k)$ with respect to the structural order of each type.

More precisely, \texttt{isLexicoDecreasing} finds an index $i$ such that:
$$ a_1 = p_1, \ldots, a_{i-1} = p_{i-1},\quad a_i < p_i, $$
where $<$ denotes strict structural sub-value. The size of each argument is
determined syntactically by \texttt{compareSize}, which follows the
\texttt{valMap} chain back to a parameter of the method. A value recorded as
\texttt{Smaller} means it was extracted from a constructor pattern or from a
field access on a \texttt{case class}, guaranteeing that it is a proper
sub-value of the original.

A structural sub-value relationship is only a valid termination argument when
the type in question is \emph{well-founded}, i.e., it admits no infinite
descending chain of sub-values. The checker enforces this via
\texttt{typeWellFounded}. A \texttt{sealed} type is well-founded if every child
is well-founded, case objects are trivially well-founded (they are leaves), and
a case class is well-founded when all of its fields are stable members
corresponding directly to constructor parameters. Because every recursive call
strictly decreases the argument tuple in this well-founded order, there can be
no infinite sequence of recursive calls, so \texttt{f} terminates.


\section{Mutual Recursion}
The checker handles mutual recursion by inlining method calls. When \texttt{f}
calls a method \texttt{g} that is not yet on the \texttt{callStack},
\texttt{g}'s body is traversed with \texttt{g} pushed onto the stack and the
actual arguments mapped to \texttt{g}'s parameters in \texttt{valMap}. Any call
inside \texttt{g}'s body that is already on the stack (whether to \texttt{g} or
back to \texttt{f}) is treated as a recursive call and must satisfy
\texttt{areSmaller} with respect to the that method's parameters.

The invariant is that the \texttt{callStack} represents the current
chain of inlined calls. When a method already on the stack is called, the
checker checks that the arguments to that method's original parameters are
strictly smaller. Since \texttt{valMap} propagates size information through
argument-to-parameter mappings as each callee is pushed, size inequalities can
be composed across an arbitrary chain of mutual calls.

For example, in the mutual recursion between \texttt{isEven} and
\texttt{isOdd} over the \texttt{Nat} ADT in \autoref{sec:mutualRec}, when the
checker encounters the call \texttt{isEven(pm)} inside \texttt{isOdd}, it traces
the chain $\texttt{pm} < \texttt{m} = \texttt{pn} < \texttt{n}$ through
\texttt{valMap}, establishing that the argument to \texttt{isEven} is
\texttt{Smaller} than \texttt{isEven}'s original parameter. Because \texttt{Nat}
is well-founded, the call is accepted and both functions terminate.

More generally, suppose the inlined call chain is
$f_0 \to f_1 \to \cdots \to f_n \to f_k$ for some $k \leq n$.
The checker requires that the arguments passed to $f_k$ are strictly smaller
than $f_k$'s parameters in the well-founded order. Since \texttt{valMap} records
the accumulated size relationships through every parameter mapping along the
chain, a \texttt{Smaller} assertion implies that each iteration of the mutual
cycle strictly decreases the relevant argument. Again, by well-foundedness, this
is possible finitely many times.


\section{While Loops}
A while loop is analyzed by two traversals of its body. In the first traversal,
recursive call checking is disabled and \texttt{varMap} is initialized to empty.
The checker looks for a mutable variable \texttt{v} such that every execution
path through the loop body assigns \texttt{v} a value that is \texttt{Smaller}
(i.e., a structural sub-value of \texttt{v}'s current value).
The merging rules for \texttt{varMap} over branches ensure that if any branch
leaves \texttt{v} at \texttt{Same} or \texttt{Unknown}, it is not counted as a
decreasing variable. Only a variable that decreases in \emph{all} branches
qualifies and if no such variable exists the checker reports an error.

Once a decreasing variable \texttt{v} is identified, termination of the loop
follows from well-foundedness of \texttt{v}'s type. Because \texttt{v} is
strictly smaller after every iteration, and the type of \texttt{v} is
well-founded (no infinite descending chains exist), the loop must eventually
reach a point where the assignment \texttt{v = v.someField} would dereference a
leaf value (such as \texttt{Nil.tail}), at which point an exception is thrown
(which counts as termination) or the loop condition becomes false before that
point is reached. Both are valid terminations under our definition.

The second traversal then verifies, that any recursive calls inside the loop
body also terminate.


\section{Higher-Order Functions}
When a call to a higher-order function is encountered, the checker inlines the
callee's body just as for ordinary calls. Inside that body, if the higher-order
argument (e.g., an \texttt{op} parameter of type \texttt{(A, B) => B}) is
applied, \texttt{getMethodSymbol} resolves the application back to the concrete
closure that was passed at the call site. The closure's body is then traversed
under the same call stack and size maps.
This means that a recursive call made inside a closure passed to a higher-order
function is treated exactly like a recursive call to an ordinary function.

As illustrated by the \texttt{addAll}/\texttt{foldRight} example in
\autoref{sec:HOF}, the checker can establish the chain
$\texttt{hd} < \texttt{this} = \texttt{args} < \texttt{e}$ through inlining
of \texttt{foldRight} and resolution of \texttt{op} to the closure. The
correctness argument reduces to the mutual recursion case.


\section{Soundness Under Escape Hatches}
In all cases, the checker does not verify the assertions made by any escape
hatches, and it is the developer's responsibility to ensure they are correct.
Under correct use of escape hatches, the conditional soundness guarantee is as
strong as the unconditional one.

\section{Annotations Added to the Standard Library}
Integrating the checker with idiomatic Scala code requires annotating parts of
the standard library that the checker cannot verify automatically.
Two categories of annotations are necessary.

Adding \texttt{@assumeWellFounded} on well-founded types that use mutable
variables under the hood. The \texttt{List[+A]} type is declared \texttt{sealed
abstract class} with two subtypes: \texttt{Nil} a \texttt{case object} and
\texttt{::} a \texttt{case class}. This almost satisfies the checker's
well-foundedness, however, \texttt{::} declares its \texttt{next} field as
\texttt{private[scala] var}, making it a mutable field rather than a stable
member, therefore, failing the check.
Other types in the standard library may benefit from similar semantic assertions
that are syntactically false.

Adding \texttt{@assumeDecreases} on \texttt{head} and \texttt{tail}. Since they
are defined as methods, the checker cannot infer a decrease automatically,
adding the annotation tells the checker that calling \texttt{.tail} on a
\texttt{List} value yields a strictly smaller value.
The same annotations are added on \texttt{Nil}, even though those methods throw
exceptions rather than returning a smaller value. This is correct under the
termination definition where exceptions are a form of termination. Annotating
them allows the checker to accept calls on these methods on any \texttt{List}
regardless of whether they are empty or not which the checker cannot infer.

Furthermore, methods like \texttt{+}, \texttt{-}, \texttt{<}, etc. on
\texttt{Int}, \texttt{Float}, and other primitive types have their
implementations in compiled bytecode. Their \texttt{defTree} is empty, so the
checker emits warnings as their bodies are available for analysis. To suppress
these warnings \texttt{@assumeTerminates} annotations where added to these
operators.


\section{Lexicographic Ordering over the Size-Change Principle}
The global size-change principle \cite{SizeChange} was considered as an
alternative to the per-call lexicographic check. It would handle the
cross-parameter swapping case and some mutual recursion patterns that the
current checker cannot.
However, the size-change principle has been shown to be
\textsf{PSPACE-complete}. For a compiler phase that runs on every build, a
\textsf{PSPACE} algorithm over the full call graph is not acceptable.
Furthermore, when the size-change check fails, the failure is a global property
of the call graph rather than a property of a specific call site. The per-call
lexicographic check, by contrast, fails at a precise source location with a
precise argument, making it straightforward to guide the developer toward a fix
or an appropriate escape hatch.


\section{Limitations}
Functions that terminate because an integer decreases toward a bound, rather
than a data structure shrinks, cannot be verified. This covers a significant
class of imperative algorithms. The most natural extension would be to allows
the \texttt{@decreases} annotation to accept a well-founded integer relation,
checked at each loop iteration or recursive call. This would not necessarily
require an SMT solver and could be implemented within the same syntactic
framework.

When a method is called on a value whose static type is an unsealed trait or
abstract class, the checker cannot enumerate the possible concrete
implementations and conservatively rejects the call. In practice, this is most
likely to arise with third-party library types that the checker has no
visibility into. The correct response in those cases is to wrap the call in
\texttt{uncheckedTermination} or to annotate the callee with
\texttt{@assumeTerminates}.
